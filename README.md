# ⛏️ telegram-mining-game

لعبة تعدين بنظام النقرات والتطوير التلقائي كـ **Telegram Mini App (TMA)** — شبيهة بـ *Notcoin* و *Hamster Kombat*.

## 📁 هيكل المشروع

```text
telegram-mining-game/
├── package.json
├── server.js          # خادم Express + بوت تيليجرام (Telegraf)
├── .env.example       # انسخه إلى .env وضع BOT_TOKEN و APP_URL
└── public/
    └── index.html     # واجهة اللعبة كاملة (تصميم + منطق + حفظ تلقائي)
```

## 🚀 التشغيل محلياً (دقيقة واحدة)

```bash
npm install
npm start
```

افتح المتصفح على: http://localhost:3000

> بدون `BOT_TOKEN` يعمل خادم الويب فقط — البوت اختياري للتجربة المحلية.

## 🌐 النشر للإنتاج (Render + PostgreSQL مجاناً)

دليل كامل خطوة بخطوة — من التشغيل على جهازك إلى ربط البوت: **[DEPLOYMENT.md](DEPLOYMENT.md)**
(يتضمن `render.yaml` جاهزاً للنشر بضغطة Blueprint، ومتغيرات البيئة، وقائمة تحقق قبل دعوة اللاعبين.)

## 🤖 ربطها بتيليجرام كـ Mini App

1. انسخ `.env.example` إلى `.env` وضع `BOT_TOKEN` من [@BotFather](https://t.me/BotFather).
2. عرّض الخادم للإنترنت: `ngrok http 3000` (أو استضف على Render / Railway / Vercel).
3. ضع رابط `https` الناتج في `APP_URL` داخل `.env` وأعد تشغيل الخادم،
   واستبدل `MiningClickerBot` في `public/index.html` باسم مستخدم بوتك لتعمل روابط الدعوة.
4. في `@BotFather`: ‏`/mybots` ← اختر البوت ← **Bot Settings** ← **Menu Button** ← **Configure menu button** ← أرسل نفس الرابط.
5. افتح البوت واضغط زر القائمة لتشغيل اللعبة من داخل تيليجرام مباشرة.

## 🎮 الميزات

- **🎮 مغامرة المنجم (الشاشة الرئيسية)**: لعبة تفاعلية فورية — حرّك عربة المعدّن باللمس أو الأسهم لمدة 60 ثانية، التقط 💎/🪙 وجوهرة ذهبية نادرة مع سلاسل ومضاعفات، واجمع قدرات خاصة (🧲 مغناطيس، 🛡️ درع، ⏳ إبطاء زمن، ⭐ نقاط مضاعفة، ❤️ قلب)، فعّل «حمّى الذهب» بسلسلة 15، وأنجز 3 مهام داخل الجولة عبر مراحل صعوبة متصاعدة — مع مؤثرات صوتية مولّدة، اهتزاز شاشة ووميض إصابة، مكافآت مرور قريب من الخطر، وشاشة نتائج بالدقة وأعلى سلسلة ولقب. جائزة ذهب حسب نتيجتك (حتى 100 🪙) وأفضل نتيجة محفوظة.
- نقر سريع متعدد اللمس مع أرقام متطايرة واهتزاز (Haptic Feedback) عبر Telegram WebApp.
- طاقة تتجدد (3/ثانية) وتُستهلك حسب قوة النقرة.
- 3 ترقيات (فأس فولاذي / عامل آلي / منصة عملاقة) بأسعار تصاعدية وعدّاد ملكية.
- دخل سلبي + **أرباح أثناء الغياب** حتى 8 ساعات.
- **حفظ سحابي في قاعدة بيانات حقيقية**: SQLite افتراضياً (`data/game.db` عبر `better-sqlite3`)، أو PostgreSQL عند ضبط `DATABASE_URL` — مع ترحيل تلقائي لمرة واحدة من `data/db.json` القديم إن وُجد. تحقق كامل من `initData` الخاصة بتيليجرام (HMAC) عند وجود `BOT_TOKEN`، ووضع ضيف تلقائي بدونه للتطوير — مع بقاء `localStorage` كنسخة احتياطية ونسخة منفصلة للتقدم المحلي عند أول دخول (لا تُنقل أرصدة غير موثوقة إلى السحابة).
- **مكافحة غش خادمية**: الخادم لا يثق بحالة العميل — القدرات والأسعار تُشتق حتمياً من عدد المشتريات، وسقف الكسب محسوب من الزمن المنقضي منذ آخر حفظ موثوق (حد النقر `MAX_CLICKS_PER_SEC=20` + الدخل السلبي)، والذهب لا ينقص إلا بقيمة مشتريات فعلية، والطاقة لا تتجدد أسرع من 3/ثانية، والتعزيز يُقبل فقط بعد التهدئة وبمدة ≤30 ثانية. القيم المستحيلة تُقتطع وتُسجَّل كمخالفة (`violations`)، ومكافآت الخادم (الدعوات) تُدمج في حفظ الداعي التالي بدل أن يطمسها عميل قديم. حدود معدّل طلبات لكل لاعب على مسارات API.
- **دعوات فعلية**: صديق ينضم عبر `?start=ref_<id>` ويفتح اللعبة ⇒ الداعي يحصل على 1,000 🪙 (حتى لو فتح اللعبة لاحقاً)، مع عدّاد أصدقاء وأرباح دعوات.
- **مكافأة يومية** بسلسلة أيام متتالية (500 🪙 وتزيد 100/يوم حتى 1,500)، و**تعزيز ×2** لمدة 30 ثانية كل 5 دقائق.
- **🎛️ أوضاع وصعوبات**: كلاسيك 60ث / البرق 30ث سريع / البقاء حتى آخر قلب / **👹 الزعيم** (75ث: زعيم بصحة تصل 170 يتحرك ويستهدفك بصخور موجّهة، تجمع من نقاطك شحن هجوم مضاد 🎯، وقتله يمنح ‎+150 🪙 وإنجازاً)، × (سهل/عادي/صعب بنقاط حتى ‎+40٪)، مع أحداث عشوائية داخل الجولة (وابل جواهر 🌧️/عاصفة صخور ☄️)، صندوق كنز وكريستال متعرج، ومهارة تفجير فعّالة 🧨 (زر أو مسافة) تدمر الأخطار الظاهرة.
- **🏆 بطولة سباقات أسبوعية**: نتائج كل سباق مباشر تُسجل خادمياً في قاعدة البيانات (جدول `race_stats`) وتظهر في تبويب الصدارة حسب أسبوع ISO — انتصارات، عدد سباقات، أفضل نتيجة — مع إعادة ضبط تلقائية كل أسبوع جديد.
- **🛠️ ترقيات مغامرة دائمة**: 8 مسارات بالذهب تُحفظ سحابياً ويتحقق الخادم من أثمانها — مغناطيس مطوّر، عربة أوسع، حذاء سريع، درع بداية، قلوب إضافية، رمال أطول، حظ قدرات، شحنات تفجير.
- **🎨🏅 أشكال وإنجازات**: 4 أشكال عربة تُفتح بأفضل نتيجة، و7 إنجازات بمكافآت ذهب (أول جولة، نتيجة 500، سلسلة 20، 300 جوهرة، ناجي البقاء، بطل سباقات، صانع ذهب).
- **⚔️ سباق مباشر لاعب ضد لاعب (WebSocket `/ws`)**: خصم عشوائي أو غرفة خاصة برمز 4 أحرف، نفس تساقط الجواهر للطرفين (بذرة موحدة من الخادم)، شبح الخصم ونقاطه لحظياً على نفس الملعب، **إعادة سباق فورية بموافقة الطرفين**، نتيجة موثقة بسقف نقاط زمني — للمجد لا للذهب حتى لا تُزرع النتائج.
- **لوحة صدارة** لأفضل 20 معدّناً حسب إجمالي المكاسب.
- **⚔️ ساحة قتال تجريبية** (تبويب خامس): قتال تبادلي ضد خصم آلي يقرر بقواعد (يعالج حين يضعف، يهاجم، يدافع، يشحن طاقته) — هجوم/دفاع/علاج/انتظار، صحة وطاقة قتال مستقلة، حد 30 جولة مع حسم بنسبة الصحة، فوز = +50 🪙 وسجل انتصارات محلي. (نسخة عرض محلية؛ النقل للخادم مثل بقية الاقتصاد خطوة لاحقة عند اعتمادها.)
- مستوى يعتمد على إجمالي ما كسبته عبر الزمن (لا ينقص عند الشراء).

## 🔌 API

| الطريقة | المسار | الوصف |
|---|---|---|
| `GET` | `/health` | `{ ok, bot, users }` |
| `GET` | `/api/me?ref=ref_<id>` | جلب/إنشاء ملف اللاعب ومعالجة الدعوة |
| `POST` | `/api/save` | حفظ حالة اللعبة (مُتحقق منها ومقيدة بحدود آمنة) |
| `POST` | `/api/claim-daily` | استلام المكافأة اليومية (مرة/يوم) |
| `GET` | `/api/leaderboard` | أفضل 20 لاعباً |

المصادقة: ترويسة `X-Telegram-Init-Data` من Telegram WebApp، أو `X-Guest-Id` في وضع الضيف.

## حدود الثقة والحفظ

- `migrate: true` في `/api/save` لا يمنح أي استثناء للتحقق. البيانات المحلية ليست مصدرًا موثوقًا للأرصدة والترقيات.
- عند إنشاء حساب سحابي تُحفظ النسخة المحلية السابقة تحت `mining_offline_backup` قبل تحميل الحالة السحابية؛ الحسابات السحابية الموجودة لا تُصفّر.
- ترحيل ملف `data/db.json` الموجود **على الخادم** مستقل عن استيراد العميل، ويبقى مدعومًا.
- التحقق الحالي للحفظ قائم على سقف الكسب، وليس محاكاة خادمية كاملة؛ نتائج المغامرات وفتح المناطق ما زالت محلية، ومكافآت الإنجازات السحابية معطلة عمدًا حتى إضافة إثبات خادمي.

## معاملات تحديث اللاعبين

`store.withUsers(ids, callback)` يحيط بإنشاء اللاعب ومعالجة الدعوة والحفظ والمكافأة اليومية بمعاملة واحدة. لا يرسل الخادم نجاح العملية قبل نجاح `COMMIT`.

- SQLite: طابور للمعاملات على الاتصال + `BEGIN IMMEDIATE` لمنع التعارض بين عمليات الخادم، مع مهلة قفل 5 ثوانٍ.
- PostgreSQL: اتصال مخصص للمعاملة وأقفال advisory transaction-level لكل معرف لاعب، بترتيب ثابت، بما يشمل اللاعب الذي لم يُنشأ بعد.
- عند الفشل يجري `ROLLBACK`؛ إعادة طلب اليومية بعد نجاحها تُعيد 409 دون مكافأة ثانية. إعادة دخول المُحال لا تضيف دعوة ثانية.
- لا تغييرات في مخطط بيانات اللاعبين أو أسعار الترقيات أو قيمة المكافآت.
- أي مسار جديد يكتب `users` أو `pending_referrals` أثناء التشغيل يجب أن يستخدم الواجهة نفسها، ويقفل **كل** معرف سيعدله. لا تضع طلبات شبكة خارجية أو أعمالًا طويلة داخل المعاملة. المعاملات المتداخلة مرفوضة.

### اختبارات التخزين

```bash
npm ci
npm run build
npm test
# اختياري: قاعدة PostgreSQL اختبارية منفصلة وفارغة — لا تستخدم قاعدة اللاعبين
TEST_DATABASE_URL=postgres://USER:PASSWORD@localhost:5432/mining_test npm test
```

عند ضبط `TEST_DATABASE_URL` تُختبر API على PostgreSQL وتُختبر معاملات التخزين على المحركين. يستخدم CI خدمة PostgreSQL 16، بجانب الاختبار الافتراضي على SQLite. اختبارات التزامن تشمل عمليتي خادم مستقلتين، والتراجع عن كتابة جزئية، وإعادة التشغيل وإعادة المطالبة بالمكافأة.

## موثوقية بروتوكول السباقات

- رسائل WebSocket يجب أن تكون JSON object مع `type` نصي. الرسائل غير الصالحة لا تُسقط الخادم، وحد الرسالة 4096 بايت؛ الرسائل الأكبر تغلق اتصال المرسل فقط.
- `ready` يعمل في lobby فقط. نتيجة اللاعب تُختم مرة واحدة، و`rematch` يحتاج موافقة الطرفين بعد انتهاء حفظ النتيجة، لا أثناء `settling`.
- لا مطابقة بين اتصالين لهوية اللاعب نفسها؛ الانتقال إلى غرفة أخرى يُنظّف السابقة ويُبلغ الخصم.
- النتائج ما زالت نقاطًا يرسلها العميل ضمن سقف زمني، وليست محاكاة خادمية مثبتة. تحصين آلة الحالات لا يعني أن لوحة الصدارة صارت مقاومة لكل أنواع الغش.
- لتشغيل اختبارات WebSocket على PostgreSQL استخدم قاعدة اختبار منفصلة تحتوي مخطط اللعبة (يمكن إنشاء المخطط بتشغيل مجموعة الاختبارات عليها أولًا):

```bash
TEST_RACE_DATABASE_URL=postgres://USER:PASSWORD@localhost:5432/mining_test node --test test/multiplayer.test.js
```

تؤخر fixture الاختبارية كتابة النتائج لإثبات عدم تداخل rematch مع الحفظ. لا تستخدم fixture خارج الاختبارات. استخدم قاعدة اختبار جديدة عند إعادة هذه الاختبارات؛ إحصاءات السباقات تبقى محفوظة فيها.
