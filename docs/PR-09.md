# PR-09 — Server-sealed race results (clock, timeout, forfeit, score caps)

Base: PR-08 (server achievements). Same branch, separate commit.

## Why

Live races (`/ws`) were the one competitive feature whose outcome the clients still decided:

* the client picked the race duration (`ADV_MODES.classic.duration`) and sent `finish` whenever
  it liked — a player who closed the app left the opponent waiting forever, and nothing was ever
  written to `race_stats`;
* leaving mid-race cost nothing (`opponent_left` just closed the room), so losing races were free
  to abandon;
* the only bound on a reported score was `45 × elapsed + 100`, applied once at `finish`; the
  per-tick `progress` stream was relayed untouched, so a last-second jump from 200 to 2,800 was
  accepted and the opponent's ghost showed absurd numbers;
* the two `race_stats` rows (winner/loser) were written in separate transactions — a crash
  between them produced a race with one participant.

Exact replay of a seeded race on the server is not feasible (RNG consumption depends on each
player's reactions), so this batch does not pretend to simulate; it moves every *decision* to the
server and tightens the bounds around the one input that must remain client-reported.

## Rules (`race-rules.js`, pure, unit-tested)

| rule | value | env |
|---|---|---|
| duration | 60 s, sent in `start.duration`, the client renders this timer | `RACE_DURATION_SEC` (2–300) |
| grace | 8 s after the duration before the server seals the room | `RACE_GRACE_SEC` (1–60) |
| time cap | `floor(min(elapsed, duration) × 45) + 100` | — |
| stream cap | `lastAcceptedProgress + 45 × Δt + 400` | — |
| forfeit window | leaving `≥ min(3 s, duration / 2)` after `startAt` is a loss | — |

* Every report (`progress` and `finish`) is clamped to `min(timeCap, streamCap)` using the server
  clock (`startAt`); the clamped figure is what the opponent sees, and a clamped final score is
  stored with `flagged: true` in the `result` message. Non-finite input counts as 0.
* **Timeout**: at `startAt + duration + grace` the server settles the room itself. Players without
  a `finish` get their last accepted progress as the result (`timedOut: true`); a player who never
  reported anything gets 0. `result.reason` is `"timeout"`.
* **Forfeit**: `leave`, socket close, or moving to another room inside the forfeit window seals
  the race immediately: the leaver loses regardless of score (`forfeited: true`), the remaining
  player wins and receives `opponent_left {forfeit: true, winnerId, results, message}`. Before the
  window (first 3 s) leaving still just closes the room with a plain `opponent_left` and nothing is
  recorded. A network drop counts as a forfeit — this is a deliberate convention (otherwise
  "my wifi died" is a free escape), and it is documented in the README.
* Ties keep `winnerId: null` and both rows are stored as non-wins.
* `store.recordRaceResults(week, results)` writes both rows in **one** transaction (SQLite and
  PostgreSQL). The room's `outcome` is fixed synchronously before the write starts, so a slow store
  (the test fixture delays it by 150 ms) cannot be raced by `rematch`/`leave`; a store failure is
  logged and the outcome is still announced.

## Server changes

* `server.js`: `beginRaceRound(room)` seeds the round, resets `results`/`track`, arms an unref'd
  timer at the deadline and sends `start {seed, startAt, duration, opponent}`; `settleRace(room,
  reason, {forfeitBy})` fills missing results, decides the winner and persists;
  `announceRace(room, outcome)` broadcasts `result` only if both players are still there;
  `leaveRoom` clears the timer and settles as a forfeit when inside the window. `progress` is
  clamped and remembered in `room.track`; `finish` reuses the same cap.
* `db.js`: `recordRaceResults(week, results)` on both stores (`withUsers` + one transaction).
* Protocol additions are backwards compatible: `start.duration`, `result.reason`,
  per-player `flagged | timedOut | forfeited`, and the optional `forfeit/winnerId/results` fields
  on `opponent_left`. Old clients ignore them.

## Client changes (`public/index.html`, identity preserved)

* `startAdventure('race', seed, duration)` uses the server duration for the race timer.
* A `result` that arrives while the race round is still running (timeout) ends the round first,
  then shows the outcome with a "انتهت المهلة" hint.
* `opponent_left` with `forfeit: true` shows the sealed win (both scores) and, since it is a
  server-sealed result, bumps the local `raceWins` counter used by the offline achievements list;
  a plain `opponent_left` keeps the old "room closed" behaviour.

## Tests

* `test/race-rules.test.js` (4): env clamping/defaults, time vs. stream cap incl. non-finite
  input, deadline/forfeit window, winner decision with forfeits and ties.
* `test/multiplayer.test.js` (+4, harness runs with `RACE_DURATION_SEC=2`, `RACE_GRACE_SEC=1`):
  timeout settlement using the last streamed progress; forfeit after the window recorded as a
  win/loss on `/api/race-leaderboard`; early leave = plain `opponent_left` with no rows; wire
  clamping of `progress`/`finish` with `flagged`.
* `test/client-sync.test.js` (+1): the client follows the server clock and only counts a sealed
  forfeit.
* Matrix: SQLite 110/110, PostgreSQL 16 111/111, multiplayer on PostgreSQL 15/15.

## Not in this batch

* Score is still a client report under two caps, not a server simulation — a cheater streaming
  exactly at the cap for the whole race is not detectable here; the ceiling is ≈2,800 for 60 s
  versus ≈2,000 for a very good honest run.
* The arena tab still decides its own outcome locally (server-capped reward); weekly missions,
  balance pass and mobile UX follow in later batches.
