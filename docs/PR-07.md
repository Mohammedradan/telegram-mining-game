# PR-07 — Daily missions on the server (+ the page-boot fix)

Base: PR-06 (server XP). Same branch, separate commit.

## Why

Missions were the next roadmap item after XP, and the only honest way to build them is on top of
events the server already verifies: accepted mining batches, successful purchases, boost
activations, accepted adventure runs and paid arena rewards. The client never reports mission
progress — it only *claims* a mission once the server shows it complete.

## ⚠️ Pre-existing defect found and fixed in this batch

`updateUI()` addressed three elements that no longer existed in the markup: `#daily-btn`,
`#boost-btn` and `#sync-status`. In a real browser `dailyBtn.disabled = …` throws
`TypeError: Cannot set properties of null`, and because the first `updateUI()` runs at the top level
of the page script **before** `bootstrap()`, the script aborted there: `bootstrap()` never ran, the
client never called `/api/me`, and every player was silently playing offline against `localStorage`.
The 100 ms UI timer kept throwing the same error on every tick.

Proof (full page script executed in a stub DOM, `test/page-boot.test.js` methodology):

| File | top-level error | `/api/me` requested |
|---|---|---|
| `public/index.html` @ `main` (`b3688f6`) | `TypeError: Cannot set properties of null (setting 'disabled')` | **no** |
| this branch | none | yes, `serverMode = true`, balance/progress/missions adopted |

Fix: the three elements are back in the markup (daily reward button inside the new missions card on
the play tab, boost button on the mining tab under the tap hint, sync line under the gold counter),
`updateUI()` tolerates a missing element (`|| {}`), and two regression guards were added:
*every id the script addresses statically must exist in the markup*, and *the whole page script must
run to completion and reach `bootstrap()`*.

## Rules

* Every UTC day (`dayStr()`, the same day the daily reward uses) each player gets **3 distinct
  missions** chosen deterministically from a fixed pool with `xorshift(hash32("userId:day"))` —
  same player + same day ⇒ same set on every device/server, no storage needed to reproduce it.
* Pool (target · reward):

  | key | counts | target | gold | xp |
  |---|---|---|---|---|
  | `mine_energy` | energy actually spent by accepted clicks | 600 | 150 | 40 |
  | `mine_gold` | gold minted by accepted clicks | 800 | 150 | 40 |
  | `runs` | accepted adventure runs | 3 | 200 | 50 |
  | `gems` | gems in accepted runs (after the physics clamp) | 60 | 200 | 50 |
  | `score` | best single accepted run (max) | 400 | 250 | 60 |
  | `boss` | real boss kills (mode boss, ≥ 8 s) | 1 | 300 | 80 |
  | `boost` | boost activations | 2 | 100 | 30 |
  | `buy` | successful `buy` / `buy_adv` | 2 | 150 | 40 |
  | `play_time` | accepted run seconds | 180 | 200 | 50 |
  | `survival` | best survival-mode score (max) | 250 | 250 | 60 |
  | `arena` | paid arena rewards | 2 | 100 | 30 |

* Progress is only ever increased inside `applyOps`, after the op has been accepted and clamped —
  a rejected or clamped-away op contributes nothing. A claimed mission stops counting.
* Claiming is a sequenced op `{type:'mission', key}` (idempotent like every other op); the server
  pays the gold + XP, writes an `op_ledger` row (`kind: mission`) and answers
  `ok {gold, xp}` or `rejected {reason: incomplete|claimed}` / `invalid` (not one of today's keys).
  `key: 'bonus'` claims the all-three bonus (300 🪙 + 100 XP) once every mission is claimed.
* Storage: `sync_json.missions = {day, items:[{key, progress, claimed}], bonusClaimed}` —
  no schema change. On a new day (or a missing/corrupt record, e.g. rows from before this batch)
  `ensureMissions` simply deals today's set. Unclaimed completed missions expire with the day.

## API

`/api/me`, `/api/ops` and `/api/claim-daily` now include

```json
"missions": {
  "day": "2026-10-14", "resetsIn": 17151,
  "items": [{ "key": "mine_energy", "icon": "⚡", "title": "أنفق 600 طاقة في التعدين",
               "target": 600, "progress": 20, "done": false, "claimed": false, "gold": 150, "xp": 40 }],
  "bonus": { "gold": 300, "xp": 100, "ready": false, "claimed": false }
}
```

Titles/icons are produced by the server so the client has no mission table to drift from.

## Client

* New `📅 مهام اليوم` card on the play tab: the daily reward button, one row per mission
  (progress bar, reward, claim button enabled only when the server says `done`), the bonus row and
  the reset countdown. Offline it shows a one-line hint (missions need the server) but the daily
  reward still works locally as before.
* `claimMission(key)` is optimistic like every other op: gold shows immediately, the row locks, the
  op is queued with `expected`, and the next sync adopts the server's answer (a rejected claim is
  simply not re-applied, so the optimistic gold disappears). The sync line announces
  `🎯 مهمة مكتملة: +150 🪙 +40 خبرة`.
* `adoptServerState` stores `data.missions` on the profile and re-renders the card after every sync,
  so progress refreshes live (each `/api/ops` response carries the updated counters).

## Tests

* `test/economy.test.js` (+4): deterministic 3-mission deal with Arabic titles; progress from
  verified ops only (boost 1/2 ⇒ `incomplete`, buy 2/2 ⇒ paid once, second claim ⇒ `claimed`,
  ledger row, bonus only after all three, bonus twice ⇒ `claimed`); adventure runs feed
  runs/gems/score/boss/survival and a boss run does not count for survival; day rollover, legacy
  row without a record, and a corrupt record all heal to today's set.
* `test/client-sync.test.js` (+2): missions adopted into the profile, optimistic claim re-applied
  over an older server state and announced once confirmed, rejected claim reverts; **every element
  the script addresses by id exists in the markup** (would have caught the defect above).
* `test/page-boot.test.js` (new, 2): the entire page script runs in a stub DOM, `bootstrap()`
  requests `/api/me`, `serverMode` becomes true, balance/progress adopted, sync line and daily
  button updated; the missions card renders progress/claimable/claimed/bonus rows and a click
  queues exactly one `mission` op with the optimistic gold.
