# PR-05 — Adventure progress on the server: run reports, trusted stats, zones

Base: PR-04 (server-authoritative economy, `POST /api/ops`). Same branch, separate commit.

## Why this batch

With gold, energy and purchases settled on the server (PR-04), the next layer the user asked for was
zone progression. Zones were unlocked from `localStorage` stats (`mining_adventure_stats`), i.e. from
numbers any client can edit. Everything the roadmap wants next — achievements, missions, XP — needs
the same inputs (runs, gems, boss kills, best score, play time). So this batch moves **the adventure
round itself** to the server as a verified event, derives stats and zones from it, and leaves
achievements/missions/XP for the following increments on top of trusted data.

## Protocol

New op type in `POST /api/ops`:

```
{ "seq": 7, "type": "run",
  "mode": "classic|blitz|survival|boss", "difficulty": "easy|normal|hard",
  "score": 700, "gems": 30, "combo": 12, "duration": 60,   // duration = game seconds of the round
  "boss": false, "race": false,
  "ago": 1800 }                                              // ms since the round ended, computed at send time
```

Per-op result: `status ok|clamped|rejected(reason time|short)|invalid` plus `{mode, difficulty, duration,
score, gems, combo, boss, race, gold, zones, unlocked, reason?}`. `reason: "too_soon"` on an accepted run means
the round was recorded but paid no gold (reward gap).

`reward` with `game: "adventure"` is now `invalid` (`reason: "use_run"`); `reward` stays for the arena.

## Server rules

| Check | Rule |
|---|---|
| Timeline | Each run claims an end time `now − ago`, clamped between the previous accepted run and `now`. The gap to the previous run must cover the round's duration (3 s network slack). After an absence the window opens at most **30 minutes** back, so a batch of rounds queued offline is accepted, but no more than 30 minutes of play can ever be reported per 30 minutes of wall-clock time. `cursor` is persisted as `sync.lastRunAt`. |
| Minimum | Rounds shorter than 5 s are not rounds (`rejected: short`, not a violation). |
| Physics | gems and combo ≤ `5 × duration + 5` (the game spawns at most one object per 0.2 s); score ≤ `300 × duration + 300`; boss kill counts only in boss mode and only after ≥ 8 s. Exceeding any of these clamps the value, marks the op `clamped` and counts a violation. |
| Reward | computed from `min(score, 40 × duration)` — a 5-second round cannot claim a 500-point payout — with the per-mode cap (100 classic/blitz/boss, 150 survival) and +150 for a real boss kill; at most one paid round per 20 s **of round time** (so honest offline batches are paid, spam is not). Race rounds (`race: true`) build stats but pay nothing. |
| Stats | `state.adventure = { runs, gems, maxCombo, bestScore, bestSurvival, bossWins, rewardEarned, playSec, zones }` — stored in `state_json` (no schema change), sanitized like the rest of the state, never accepted from the client. |
| Zones | `zones = 1 → 2 (gems ≥ 25 or runs ≥ 3) → 3 (gems ≥ 75 or bossWins ≥ 1)`, the same thresholds the UI always used, derived in `deriveStats`. |
| Ledger | every accepted run is appended to `op_ledger` (`kind: run`, gold delta, full detail). |
| Races | `/api/me` now also returns `race: { races, wins, bestScore }` aggregated from `race_stats`, which the WebSocket server seals itself — a trusted source for the "race winner" stat. |

Existing rows without `adventure` start at zero with one zone; verified on the legacy SQLite schema test
(and the PostgreSQL code path is the same sanitizer).

## Client (`public/index.html`)

* `endAdventure()` reports **every** round as a `run` op (also races and zero-reward rounds); the
  optimistic `expected` gold is replaced by the server's answer on the next sync.
* Discrete ops are stamped with `at` when enqueued; `flushOps` sends `ago = sentAt − at`, so a round
  that waited in the offline queue is still placed correctly on the server timeline.
* `adoptServerAdventure(stats, race)` is called whenever a server state is adopted: it lifts the local
  mirror (`advStats`, best score, race wins) to the server values — never lowers it — and stores the
  server zone count.
* `getUnlockedAdventureZones()` = `max(server zones, device-derived zones)`. The device part is a grace
  for veterans whose progress existed only locally before this batch; zones are difficulty/visual
  progression with no gold effect, so this is safe. Anything that pays (achievements, missions) will use
  server stats only.
* Sync status line reports: new zone unlocked (server-confirmed), a round recorded without reward
  (`too_soon`), or a round refused because it did not fit real play time.

## Known bounds / next

* A client talking to the API directly can still earn at most one reward per 20 s of (bounded)
  round time — same theoretical ceiling as PR-04 (~450 gold/min vs ~100–150 honest); the balance
  pass can tighten it (e.g. longer gap for timed modes) once real play data exists.
* `runs` is a weak stat (cheap to accumulate within the window); future features should weight
  `gems`, `playSec`, `bestScore`, `bossWins` instead.
* Next increments on this base: XP/level, daily missions, server-side achievements (re-enable cloud
  rewards), race results, balance, mobile UX.
