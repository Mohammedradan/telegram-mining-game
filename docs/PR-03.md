# Harden WebSocket race state transitions and message validation

Base: current GitHub `main` at `f4e7d91e89512242af53f7187c1d6d61fb66cc9f` (includes merged PRs #11 and #12). This is a new incremental diff, not a reapplication of those changes.

## Confirmed defects
- An authenticated WebSocket message containing JSON `null` crashed the entire server via an unhandled rejection. A new regression was run before the fix and reproduced the crash on Node.js 22.23.3.
- Repeated `ready` could restart an active or finished race and clear sealed results.
- Two sockets for the same account could be paired into a race with only one result-map key.
- Joining another room left the old opponent and room pointing to the moving socket; quick/create silently detached opponents.
- The room was marked finished before asynchronous database writes completed, allowing rematch to interleave with the previous result.
- Invalid scores were coerced into results, and the size check happened only after WebSocket had buffered the message.

## Changes
- Require a JSON object with a string message type; ignore invalid JSON shapes and catch unexpected handler failures without logging raw payloads or auth data.
- Apply `maxPayload: 4096` at WebSocket receiver level. Oversized messages close only their sender with code 1009.
- Accept `ready` only in a two-player lobby, and check membership before accepting progress/finish.
- Reject non-finite/non-number progress fields and non-finite/negative finish scores; keep valid numeric scores subject to the existing cap.
- Disallow self-pairing for quick and private rooms without prohibiting multiple connections to the account globally.
- Validate the new room before leaving the old one and notify the previous opponent on room switches.
- Keep a `settling` state until result storage completes; prohibit premature rematch and suppress a stale result if the room was removed while storage awaited.
- Add a test-only preload that delays race storage to exercise actual asynchronous interleaving. No production delay flags were added.
- Add a PostgreSQL WebSocket regression pass to the existing CI job.

No changes to rewards, upgrade prices, score caps, seeded generation, duration or existing player schema.

## Validation actually run locally
Node.js v22.23.3:
- Baseline before modifications: **30/30 passed**.
- New null-message regression before the fix: **failed as expected**, reproducing server termination.
- Final `npm run build` and full SQLite suite: **38/38 passed**, no skips.
- Full suite with API and transaction tests on real PostgreSQL 18.4: **39/39 passed**, no skips; WebSocket in this full pass still used SQLite.
- Separate `TEST_RACE_DATABASE_URL=... node --test test/multiplayer.test.js`: **11/11 passed** against real PostgreSQL 18.4, including the eight new regressions.
- `git diff --check`: passed.

One development test initially assumed an empty matchmaking queue. Existing test sockets made the player immediately matched rather than waiting; the test was changed to verify creation of a new private room, and the full suite was rerun successfully.

## Remaining limitations
Results are still client scores bounded by time, not verified simulation. Durable race IDs, atomic recording of both participants, multi-instance shared rooms, timeouts, collusion protection, and durable action IDs are not implemented here. Existing best-effort persistence still allows partial leaderboard writes if a database operation fails; this PR does not claim otherwise. Mobile/Telegram manual QA and load tests were not run.
