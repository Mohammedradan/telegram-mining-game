# Make player saves and daily/referral rewards atomic

Stacked base: local branch `fix/reject-untrusted-cloud-migration` (PR 01 must land first, or use its branch as the review base).

## Problem
User creation, referral rewards, daily claims and saves performed asynchronous read/modify/upsert sequences without a shared transaction. Concurrent requests could overwrite another update or acknowledge the same daily claim more than once. A process-local mutex alone would not protect PostgreSQL or two server processes.

## Implementation
- Add `store.withUsers(ids, work)` with commit/rollback and explicit rejection of nested transactions.
- SQLite: serialize transactions on the connection, acquire a database write lock with BEGIN IMMEDIATE, and set a five-second busy timeout.
- PostgreSQL: use a dedicated connection, transaction-scoped advisory locks for every affected user in stable ID order, and AsyncLocalStorage for queries inside the transaction.
- Wrap account creation, referral processing (including pending referrals), saves and daily claims; send successful HTTP responses only after COMMIT.
- No schema migrations, currency resets, changed reward amounts, upgrade prices or race rules.
- Add integration regressions covering concurrent creation/referrals/daily claims, stale save after a reward, response-loss retry and two server processes sharing one database.
- Add store contract tests for 20 concurrent increments, partial-write rollback, rejection of nested transactions, and successful work after failure.
- Check syntax of the inline browser scripts, retain all prior tests, and extend CI with a PostgreSQL 16 service plus a PostgreSQL API/transaction test pass.

## Remaining risks and reviewer guidance
The bounded client-state economy is not authoritative; this PR prevents transaction races but does not prevent fabricated gains within the current save budget. See `docs/AUDIT-2026-10-14.md` for prioritized remaining work. Every future runtime writer to users or pending referrals must use the same transaction/locking API and lock every affected ID.
