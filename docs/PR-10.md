# PR-10 — Arena matches replayed and sealed by the server

Base: PR-09 (server-sealed races). Same branch, separate commit.

## Why

The arena tab was the last place where the browser told the server "I won" (`reward {game:'arena'}`)
and the server only answered with a 10-second rate limit. Any client could post that op every
10 s for 50 gold + 10 XP + mission progress without ever fighting. Unlike races, the arena is a
deterministic turn-based game against a bot, so the server can **replay the whole match** instead
of trusting a verdict.

## Design

* **One engine, two runtimes.** `public/arena-rules.js` is a small UMD module: the page loads it
  with `<script src="/arena-rules.js">`, the server `require()`s the same file. It contains the
  configuration (100 HP, 10 energy, +2 regen, 30 rounds, costs 3/1/4/0, 750 ms enemy turn), the
  move resolution, the bot AI and a seeded `mulberry32` RNG. No `Math.random` anywhere in it.
  Two historical quirks were fixed because the engine is now canonical: the enemy heals up to
  *its own* max HP (not 100), and it never picks a move it cannot pay for (DEFEND at 0 energy).
* **Tickets.** The server stores `sync.arena = { record: {wins, losses, draws}, ticket }` and
  issues a ticket `{ matchNo, seed (32-bit, crypto), level (server level), issuedAt }` on first
  contact (`/api/me` or `/api/ops`) and after every settled match. `/api/me`, `/api/ops` and the
  daily claim return `arena: { ticket: {matchNo, seed, level}, record, winReward, minIntervalMs }`.
  A ticket stays the same until it is consumed, so a reload or a second device sees the same match.
* **The op.** When a ticketed match ends the client enqueues `{ type:'arena', matchNo, moves }`
  (≤ 30 action names). The server checks `matchNo === ticket.matchNo` (else `rejected
  stale_match`, nothing consumed), validates the move list (else `invalid`, nothing consumed),
  then `ArenaRules.replay({ level, seed, moves })`:

  | verdict | status | effect |
  |---|---|---|
  | illegal move (energy / heal at full HP), moves after the end, match not finished | `rejected {reason, round?}` | ticket consumed, `violations + 1`, no gold |
  | finished sooner than `enemyTurns × 750 ms − 250 ms` after the ticket was issued | `rejected too_fast` | same — the UI itself cannot play that fast |
  | win | `ok {outcome:'win', gold:50, xp:10}` | record, `lastRewardAt.arena`, mission `arena` |
  | win within 10 s of the last paid win | `too_soon {gold:0, retryAt}` | record only |
  | loss / draw | `ok {outcome}` | record only |

  Every consumed ticket is followed by a fresh one in the same result (`r.ticket`) and in the
  response (`arena`). Every processed match is written to `op_ledger` (`kind: arena`, detail
  `{matchNo, status, outcome, reason, rounds, level, seed}`).
* **Legacy op.** `reward {game:'arena'}` from cached pages now answers `invalid use_arena` (like
  `use_run`); it still consumes the sequence number so an old queued batch is not rejected as a
  whole.

## Client (`public/index.html`, identity preserved)

* The arena code is now a thin UI over the engine: `startBattle()` builds
  `ArenaRules.newBattle({ level: ticket.level, seed: ticket.seed })`; `arenaAction()` calls
  `playerMove` / `enemyMove` / `nextRound` and only renders the events; buttons are enabled from
  `ArenaRules.canAct`.
* A restart during the enemy's 750 ms turn no longer injects the pending enemy move into the new
  match (`battle !== current` guard) — that would have desynchronised the replay.
* A ticket already used by an unacknowledged match cannot start another rewarded match; instead a
  **practice match** (no reward, no op) runs and the queue is flushed, so the tab never dead-ends
  offline. Without a server (local mode) the arena behaves exactly as before.
* The record shown is the server's sealed one (optimistically bumped until the verdict arrives);
  server verdicts are echoed in the match log (`✅ اعتمد الخادم فوزك`, `🛡️ لم يعتمد الخادم…`,
  `⏱️ … بلا مكافأة`). `profile.arena` is refreshed from every response.

## Tests

* `test/arena-rules.test.js` (7): determinism and replay equivalence, config/level scaling,
  illegal moves, forged move lists, 30-round verdict/draw, 300-seed fuzz (energies/health in
  range, every match finishes and replays identically), browser build = Node build.
* `test/economy.test.js` (4 new, 1 rewritten): ticket issuance and stability; verified win →
  gold/XP/record/ledger/next ticket, stale ticket, `too_soon`, paid again after the interval,
  recorded loss; forged matches (illegal, extra, unfinished, too fast, other seed, malformed input,
  legacy `reward`); legacy row without arena data. The XP test now earns its 10 arena XP from a
  replayed win.
* `test/client-sync.test.js` (2 new): static guards on the client flow and an engine-level test
  that an arena op is applied optimistically and the server verdict replaces `profile.arena`.
* `test/page-boot.test.js` harness now loads local `<script src>` files in document order.
* End-to-end (manual, against the preview): the real page script in a VM with real timers played
  a 30-round match in 23 s; the server replayed it, paid 50 gold + 10 XP, sealed `wins: 1` and
  issued ticket #2 which the client adopted.
* Matrix: SQLite 122/122, PostgreSQL 16 123/123, multiplayer on PostgreSQL 15/15.

## Known limits (documented, not hidden)

* The seed is known to the client before the match, so a scripted player can search for a winning
  move list (the test suite does exactly that). The economic ceiling is therefore still the
  10-second interval (300 gold/min) — unchanged from before — but a reward now requires a complete,
  legal match whose real duration matches the UI's own pacing. A balance pass on that interval is
  a separate batch.
* Enemy level is frozen in the ticket at issue time; levelling up between matches takes effect
  with the next ticket.
