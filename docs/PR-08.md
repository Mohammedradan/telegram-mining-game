# PR-08 — Achievements verified on the server (cloud rewards re-enabled)

Base: PR-07 (daily missions). Same branch, separate commit.

## Why

Achievements were the last progression system still living in `localStorage`. Their cloud rewards
had been deliberately disabled since the audit ("🔒 يتطلب تحققًا") because the client computed
`met()` from editable `advStats`. Every input they need now exists on the server — verified run
stats (PR-05), XP (PR-06), missions (PR-07), sealed race results, referrals, purchases — so the
whole feature moves there and the lock comes off.

## Rules

* `ACHIEVEMENTS` (15) are defined on the server. Each has a pure `value(user, ctx)` over
  server-owned data; the client never sends a number.

  | id | source | target | gold | xp |
  |---|---|---|---|---|
  | `first_run` | `state.adventure.runs` | 1 | 25 | 10 |
  | `score500` | `state.adventure.bestScore` | 500 | 75 | 20 |
  | `combo20` | `state.adventure.maxCombo` | 20 | 75 | 20 |
  | `collector` | `state.adventure.gems` | 300 | 100 | 30 |
  | `survivor` | `state.adventure.bestSurvival` | 300 | 100 | 30 |
  | `boss` | `state.adventure.bossWins` | 1 | 100 | 30 |
  | `racer` | `race_stats` wins (server-sealed WebSocket races) | 1 | 50 | 20 |
  | `earner` | `state.adventure.rewardEarned` | 500 | 100 | 30 |
  | `upgrades10` | Σ `state.owned` + Σ `state.adventureUpgrades` | 10 | 150 | 40 |
  | `missions10` | `sync.missionsClaimed` (incremented by PR-07 claims) | 10 | 200 | 50 |
  | `streak7` | daily streak | 7 | 300 | 60 |
  | `inviter` | `referralCount` | 1 | 100 | 30 |
  | `level5` / `level10` | `levelFromXp(state.xp)` | 5 / 10 | 150 / 400 | 0 (no XP loop) |
  | `tycoon` | `state.totalEarned` | 50,000 | 500 | 100 |

  The first eight keep the ids of the old client list, so offline play still shows the same
  achievements and nothing in the UI had to be renamed.
* Claiming is a sequenced op `{type:'achievement', id}` inside `/api/ops` — idempotent like every
  other op, written to `op_ledger` (`kind: achievement`), answered with `ok {gold, xp}` or
  `rejected {reason: locked|claimed}` / `invalid`. Gold and XP are applied in the same transaction
  as the rest of the batch.
* Storage: `sync_json.achievements = {claimed: {id: timestamp}}` — no schema change. One in-place
  index was added (`idx_race_stats_user`) because `race_stats` is now read per ops batch.
* Legacy rows: no record ⇒ nothing claimed; values come from the server stats that started at zero
  in PR-05. Local claims made before this batch are neither imported nor charged — the only
  theoretical double-dip is a pre-PR-04 player whose local claim was absorbed by `/api/save` back
  then (≤ 625 gold once, accepted deliberately over a migration that would trust client data).

## API

`/api/me`, `/api/ops` and `/api/claim-daily` include

```json
"achievements": { "total": 15, "claimedCount": 2, "items": [
  { "id": "boss", "icon": "👹", "name": "قاتل الزعماء", "desc": "اهزم زعيم المنجم مرة واحدة",
    "target": 1, "value": 1, "done": true, "claimed": false, "gold": 100, "xp": 30 } ] }
```

Race wins are loaded (read-only, outside the player transaction) before `/api/ops` and
`/api/claim-daily` run, so `racer` is evaluated inside the same `applyOps` call as the claim.

## Client

* `renderAchievements()` builds the rows from `profile.achievements` when connected (progress,
  rewards and the claim button all from the server) and from the old local list offline. The card
  summary shows `claimed/total`.
* `claimAchievement(id)` in cloud mode: only if the server marked it `done`; optimistic gold, the
  row locks, one `achievement` op is queued with `expected`, and the next sync adopts the server
  answer (a refusal simply does not re-apply the gold). Sync line: `🏅 إنجاز مُعتمد: +100 🪙 +30 خبرة`.
* The "🔒 يتطلب تحققًا" lock and the "قيد التطوير" alert are gone.
