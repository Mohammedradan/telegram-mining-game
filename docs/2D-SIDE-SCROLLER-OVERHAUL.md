# خطة تطوير المغامرة إلى لعبة منصات جانبية 2D

> هذه الوثيقة مبنية على فحص ملفات المشروع الحالي، وليست تأكيدًا أن الميزات المذكورة اجتازت اختبارًا جديدًا. يجب التحقق من الكود والاختبارات أثناء التنفيذ.

## القرار الفني

- الأسلوب: 2D كرتوني، عرض جانبي (side-scrolling platformer).
- الأولوية: توازن الجودة والأداء وقابلية التوسع داخل Telegram Mini App.
- لا نعيد كتابة المشروع كاملًا ولا نستبدل الاقتصاد أو الخادم دون ضرورة.
- نقطة البداية هي مغامرة المنجم الحالية في `public/index.html`، مع إعادة استخدام أنظمة التقدم والموارد والمكافآت حيث أمكن.
- يحتوي المشروع أيضًا على ساحة قتال مرئية ومحرك قواعد `public/arena-rules.js`؛ لا نخلط قتال الساحة التبادلي مع فيزياء المنصات، ولا نكسر النظام الحالي.

## ملاحظات من الفحص الأولي

- يصف `README.md` المغامرة الأصلية ذات الـ60 ثانية، بينما يضم المستودع أيضًا تجربة منصات جانبية حتمية في `public/platform-*`؛ تم جعل تجربة المنصات واجهة اللعب الافتراضية في تحديث 2026-10-17.
- `public/index.html` يحتوي الواجهة ومنطق العميل وCSS، بما فيه ساحة القتال ذات الحركات والمؤثرات وأزرار التحكم.
- `server.js` و`db.js` يديران الخادم والحفظ والتحقق من العمليات والاقتصاد.
- `package.json` يعرّف اختبارات Node ومهمة build لفحص صياغة بعض ملفات الخادم.
- `docs/GAME-DEVELOPMENT-SUMMARY.md` يصف تغييرات سابقة في واجهة الهاتف وساحة القتال. أرقام الاختبارات المكتوبة فيه تاريخية ويجب إعادة تشغيل الاختبارات قبل إعلان نجاح النسخة الجديدة.
- هذه الملاحظات لا تثبت وحدها أن النشر الإنتاجي مضبوط أو أن جميع الميزات تعمل حاليًا.

## مراحل التنفيذ

### P0 — خط أساس آمن وقابل للقياس
1. افحص `main` والملفات الفعلية وGit history وPR #16، ثم شغّل `npm test` و`npm run build` وسجّل النتائج الحقيقية قبل أي تعديل.
2. تتبّع تدفق المغامرة الحالية: بدء الجولة، حلقة التحديث، التصادمات، عناصر الجمع، نهاية الجولة، عملية `run`، وحفظ المكافأة.
3. حدّد نقاط الدخول والخروج من تبويبات اللعبة، ومقاسات حاوية اللعبة داخل Telegram، وإدارة التركيز/الخلفية وإيقاف الحلقة عند مغادرة المشهد.
4. لا تحذف اختبارات أو ميزات موجودة لتسهيل التنفيذ.

### P1 — نموذج لعب جانبي متكامل
نفّذ داخل منطقة المغامرة الحالية نموذجًا واحدًا متكاملًا قابلًا للعب:
- شخصية أصلية 2D متحركة بدل الاعتماد على صورة واحدة أو إيموجي بوصفه الشخصية الأساسية.
- حالات animation واضحة: idle، run، jump، fall، mine/attack، hurt، victory.
- تحكم لمس مناسب: عصا افتراضية أو أزرار يسار/يمين، قفز، وتعدين/هجوم؛ لوحة مفاتيح على الكمبيوتر.
- حركة جانبية وكاميرا تتبع اللاعب عند تجاوز حدود الشاشة، مع منصات وأرضية وتصادمات يمكن توقعها.
- قفز وسقوط وجاذبية وحدود للعالم، ومنع القفز اللانهائي أو المرور عبر الأرض.
- صخور/عروق معدنية قابلة للتعدين، عناصر قابلة للجمع، خطر واحد على الأقل، ونهاية مرحلة واضحة.
- تغذية راجعة بصرية وصوتية خفيفة عند الضرب وجمع الموارد وتلقي الضرر؛ إمكانية كتم الصوت وتقليل الحركة.
- تعليمات تفاعلية قصيرة لأول تشغيل، ثم هدف مباشر يمكن فهمه خلال دقيقة.
- مشهد اختبار أو مستوى أول مكتمل من البداية إلى شاشة النتيجة.

### P2 — ربط آمن بالأنظمة الحالية
- افهم صيغة عملية الجولة الحالية قبل تغييرها؛ حافظ على عقد API المتوافق ما أمكن.
- العميل يعرض الحركة فقط؛ الخادم يظل مصدر الحقيقة للمكافآت والرصيد والخبرة والإنجازات.
- لا تسمح للعميل بتحديد رصيد الذهب أو منح نفسه موارد أو الادعاء بقتل زعيم دون تحقق مناسب.
- إذا احتاجت المنصات إلى بيانات جديدة، أضفها بشكل متوافق واختبرها ولا تغيّر مخطط قاعدة البيانات بلا حاجة.
- لا تكسر المهام اليومية/الأسبوعية، الدعوات، الحفظ السحابي، الساحة، السباقات أو لوحة الصدارة.
- أوقف الجولة أو علّقها بأمان عند الانتقال لتبويب آخر أو وضع التطبيق في الخلفية، وفق سلوك واضح للاعب.
- تعامل مع انقطاع الشبكة وإعادة الاتصال وتكرار إرسال نتيجة الجولة.

### P3 — محتوى وتقدم قابلان للتوسع
بعد استقرار النموذج الأول:
- أضف مناطق تعدين بمظاهر وأنواع منصات مختلفة.
- أدوات تعدين قابلة للفتح والتطوير مع تأثير لعب واضح ومتوازن.
- أعداء وأنماط هجوم يمكن تعلمها، ثم زعيم واحد بقواعد واضحة.
- مهام مرتبطة بأفعال لعب حقيقية، إنجازات وتحديات متدرجة ومكافآت شفافة.
- مظاهر شخصية وأزياء وأشكال أدوات تجميلية؛ لا تجعل الدفع شرطًا للفوز.
- منافسات مع الأصدقاء بعد التأكد من نزاهة النتائج وقابلية الخادم للتوسع.

## الأداء وتجربة Telegram

- فضّل Canvas/محرك 2D خفيف أو Phaser إذا أثبتت المقارنة أنه مناسب؛ لا تضف محركًا ضخمًا دون مبرر.
- افصل منطق اللعب عن العرض وبيانات الشخصيات والمراحل لتجنب تضخم `public/index.html`.
- استخدم delta time محدودًا وحلقة تحديث واحدة، وتجنّب إنشاء عناصر DOM كثيرة كل إطار.
- حمّل الأصول عند الحاجة، واستخدم صور sprite مضغوطة وأحجامًا مناسبة للشاشة.
- اختبر أجهزة جوال متوسطة الإمكانيات، شاشات قصيرة، اللمس المتعدد، تدوير الشاشة، والمتصفح المكتبي.
- لا تفرض تغيير اتجاه الشاشة إذا كان Telegram أو الجهاز لا يدعمه؛ صمّم واجهة مرنة.
- احترم reduced motion، كتم الصوت، وإيقاف المؤثرات عند إخفاء التطبيق.

## الاختبارات المطلوبة

أضف اختبارات للحركة والتصادم والقفز وحدود العالم، جمع الموارد، الضرر ونهاية الجولة، منع تكرار المكافأة، حفظ التقدم، إيقاف/استئناف المشهد، وتوافق عملية الجولة مع الخادم. اختبر كذلك الواجهة الحالية والاقتصاد والساحة والسباقات. سجّل ما نُفذ فعلًا وما تعذر اختباره؛ لا تنسب نجاحًا إلى اختبار لم يتم تشغيله.

## تعريف الإنجاز

تُعد المرحلة الأولى ناجحة فقط إذا استطاع مستخدم جديد:
1. فتح اللعبة على هاتف داخل Telegram.
2. فهم الأزرار بسرعة والتحرك والقفز والتعدين داخل مستوى جانبي حقيقي.
3. جمع موارد وتجاوز خطر أو خصم والوصول إلى نهاية الجولة.
4. رؤية النتيجة والمكافأة وحفظها دون مضاعفة المكافأة بإعادة الطلب.
5. العودة للعبة دون فقدان التقدم أو كسر الميزات السابقة.

أنت مهندس ألعاب ويب كبير. افحص المستودع الحقيقي، ولا تفترض أن وصف README مطابق تمامًا للكود. ابدأ بتسجيل نتائج الاختبارات قبل التعديل، ثم نفّذ P0 وP1 أولًا في هذا الفرع. اختر التقنية بناءً على القياس والملفات الحالية. لا تكتفِ بخطة أو mockup؛ سلّم نموذج لعب جانبي حقيقيًا ومتكاملًا. نفّذ الاختبارات بعد كل مرحلة، أصلح الأعطال، وحدث هذه الوثيقة بنتائج التنفيذ والملفات المتغيرة والقرارات التقنية والمخاطر المتبقية. لا تدمج إلى main ولا تنشر إلى الإنتاج دون مراجعة وتفويض.

## تحديث التنفيذ — 2026-10-17

تم تنفيذ جولة إعادة تنظيم للواجهة دون تغيير API المكافآت أو منطق الخادم:

- مشهد المنصات الجانبي أصبح الشاشة الافتراضية بدل لوحة العربة القديمة.
- أُخفيت عناصر الرصيد والعنوان وشريط أقسام اللعب من وضع المنصات لإعطاء مساحة أكبر للمستوى؛ تظل وظائفها متاحة من التنقل السفلي وزر «القوائم».
- أبقينا العربة الكلاسيكية كاملة وقابلة للوصول من زر «القوائم»، ومنه يمكن فتح المهام والتطوير والسباق كما قبل.
- أُضيفت تسميات عربية ظاهرة لأزرار اللمس (يسار، يمين، حفر، ضرب، قوة، قفز)، مع بقاء أوصاف الوصول ودعم لوحة المفاتيح.
- تمت مواءمة عرض تبريد المهارة مع بنية الزر الجديدة دون إزالة تسميته.
- أُضيف اختبار واجهة يثبت أن المنصات هي الافتراضية وأن الرجوع إلى الواجهة الكلاسيكية والعودة ممكنان.

التحقق في هذا التحديث: `npm test` (158 اختبارًا ناجحًا) و`npm run build` ناجحان. لا تغييرات على الخادم أو صيغة التذاكر أو قواعد المكافآت. هذا التحديث يعالج ترتيب الواجهة وتجربة اللعب الأساسية الموجودة؛ لا يدّعي إضافة مناطق أو محتوى جديد إلى محرك المنصات.

### متابعة التنفيذ
- أصبحت شاشة البداية تشرح هدف الجولة بدقة (3 بلورات + تعدين صخرة + بوابة الخروج) وتعرض مفاتيح التحكم.
- بوابة الخروج تُظهر بصريًا إن كانت مقفلة أو مفتوحة، وفق الشروط نفسها الموجودة في قواعد اللعبة.
- HUD الجولة يعرض تقدّم الشروط بوضوح بجانب عدد الأعداء المهزومين؛ لا تغييرات في شروط الفوز أو قيمة المكافآت.
- تحقق إضافي بعد هذه التحسينات: اختبارات المنصات وواجهتها وAPI (28 اختبارًا) والبناء نجحوا.
