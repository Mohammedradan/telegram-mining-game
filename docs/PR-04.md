# PR-04 — Server-authoritative economy (`/api/ops`) + responsive layout fix

Base: GitHub `main` at `b3688f69bfb96534eda7d498b11a8cd5afe5360b` (includes merged PRs #11, #12, #13).
Two commits: (1) desktop/mobile layout fix, (2) the economy batch described here.

## Why this batch

The audit (`docs/AUDIT-2026-10-14.md`) left one gap bigger than all the others: the client still
sent its *entire* state to `POST /api/save`, and the server merely checked it against an earnings
cap (`GAIN_SLACK`, "proposed capabilities" funding upgrades). Everything else — zones, XP, missions,
achievements — would have been built on top of numbers the client can invent. So this batch makes
the server the single source of truth for gold, energy, upgrades, boost and rewards **before**
adding any new feature on top.

## Protocol

```
POST /api/ops
{ "session": "<client session id>", "revision": <last seen revision | optional>,
  "ops": [ { "seq": 1, "type": "mine", "clicks": 12, "boosted": 0 },
           { "seq": 2, "type": "buy", "item": "click" },
           { "seq": 3, "type": "buy_adv", "key": "magnet" },
           { "seq": 4, "type": "boost" },
           { "seq": 5, "type": "reward", "game": "adventure", "score": 640, "mode": "classic", "boss": false } ] }

→ { ok, revision, staleClient, sessionSeq, applied, results:[{seq,type,status,…}], violations,
    state, referralCount, referralEarnings, daily, serverTime }
```

* ≤ 64 ops per batch, `seq` strictly increasing, otherwise HTTP 400. Non-object bodies / arrays → 400.
* Per-op status: `ok | clamped | rejected (insufficient|max) | invalid | duplicate | active | cooldown | too_soon`.
* The server stores the last `seq` per `session` (`sync_json`). A retried batch (network timeout, double
  tab) is answered with `applied: 0` and the current state — **idempotent**.
* `revision` increments on every committed mutation; `/api/me` returns it plus `offline:{seconds,gold}`.

## Server rules (mirrors the game's own physics)

| Area | Rule |
|---|---|
| Mining | clicks ≤ `floor(min(elapsed, 600 s) × 20) + 20` **and** energy ≤ stored + 3/s regen (max 1000). Each click costs `clickPower` energy and yields `clickPower` gold; boosted clicks yield 2×. Excess is clamped (`clamped`) and counted as a violation. |
| Purchases | price from `costFor`/`advCostFor` on the **stored** state; `rejected: insufficient` if gold is short (violation), `rejected: max` at level cap. Capabilities (`clickPower`, `passiveIncome`) are derived by `deriveStats`, never accepted from the client. |
| Boost | 30 s window, 5 min cooldown measured from the server clock; `active` / `cooldown` otherwise. Passive income inside the window is doubled server-side. |
| Passive income | settled from server time on every request, 8 h offline cap (`OFFLINE_CAP_SEC`). |
| Rewards | adventure: `min(cap, floor(score/5 × scale))` (+150 only in real boss mode), ≥ 20 s apart; arena: flat 50, ≥ 10 s apart; casino → `invalid` (local-only demo). Rate-limited rewards return `too_soon`. |
| Ledger | `buy`, `buy_adv`, `boost`, `reward` appended to `op_ledger` (user, session, seq, kind, gold delta, timestamp). |

## Legacy and migration

* `POST /api/save` is kept as a shim for old clients: it **never** applies client state, returns the
  server state with `legacy: true, corrected: true`. `migrate: true` is ignored.
* Schema upgrade is in place: `users.revision`, `users.sync_json` and the `op_ledger` table are added
  with guarded `ALTER TABLE … ADD COLUMN` (SQLite via `PRAGMA table_info`, PostgreSQL via
  `IF NOT EXISTS`). Existing balances/upgrades are untouched; offline passive income is settled on
  the first `/api/me` after the upgrade. Verified on SQLite (automated, old-schema fixture) and on a
  hand-built PostgreSQL 16 database with the pre-PR schema.
* `data/db.json` import on the server is unchanged.

## Client (`public/index.html`, identity preserved)

A small sync engine replaces every `/api/save` call:

* clicks are accumulated locally and flushed as one `mine` op (regular + boosted counters);
* purchases, boost and rewards are enqueued as ops immediately after the optimistic local change;
* the queue (`session`, `seq`, pending ops) lives in `localStorage` per user, survives reloads and
  is resent after network failures with exponential back-off (`SYNC.retryAt`);
* after each accepted batch the client **adopts the server state** (gold, energy, upgrades, boost,
  daily) — the server wins on every disagreement; if the server is ahead (`staleClient`), the session is rotated;
* `/api/me` on start shows the offline passive summary coming from the server.

## Layout fix (commit 1)

Desktop screenshot showed the UI stretched across the full viewport width. The column is now capped at
`max-width: 520px`, heights use `dvh` with a Telegram viewport hook, tab bar scrolls, the adventure
canvas is clamped. Covered by `test/layout.test.js` (static assertions).
